# Forge3D telemetry options

_Research date: 2026-08-20. Sources are vendor documentation or vendor-maintained source repositories; no accounts, dependencies, or app code were changed._

## Recommendation

Use PostHog Cloud as the first one-service experiment, with a strict manual-event contract and opt-in consent. Initialize the renderer with autocapture, pageviews, session replay, console-log capture, and exception capture disabled; send only named UX events and sanitized error metadata. PostHog is the only option reviewed here that combines product analytics and error tracking in one product with an official JavaScript path that explicitly documents Electron constraints.

Do not ship telemetry until Forge3D has a visible opt-in/opt-out setting, a documented event allowlist, and a release-build smoke test proving that `.scad` source, file paths, terminal text, and OpenSCAD output are never sent.

## Practical implications for Forge3D

- The cleanest event vocabulary is product-level: `app_started`, `example_opened`, `template_inserted`, `build_started`, `build_succeeded`, `build_failed`, `stl_exported`, `assembly_part_added`, and `print_mode_entered`. Event properties should be enums, counts, durations, and coarse platform/version fields—not code, filenames, paths, geometry text, terminal output, or user-entered parameter values.
- PostHog’s default web behavior is too broad for a desktop CAD editor: its official configuration documents autocapture, pageview, pageleave, dead-click, exception, performance, and console-log capture defaults/options. Disable each explicitly rather than assuming `autocapture: false` disables every stream. ([configuration](https://posthog.com/docs/libraries/js/config))
- PostHog’s Electron fit is conditional. Its docs say Electron may reject remote code loading and recommend a no-external bundle; that makes a bundled renderer integration plausible, but it does not prove native crash coverage or main-process coverage. Validate both processes in a spike before committing.
- Sentry is the better single-purpose choice if the immediate priority is crash diagnosis rather than product learning. It is not a substitute for product analytics, so choosing Sentry alone means accepting that Forge3D will not have reliable funnels such as “opened example → rendered → exported STL.”
- Aptabase is the lower-account/privacy alternative for manual UX events and can be self-hosted, but it still needs a second service for crash/error tracking. It is therefore a two-service option, not a PostHog replacement for the stated all-in-one requirement.

## Decision gate

Before implementation, decide whether Forge3D’s first telemetry milestone is:

1. **Product learning:** PostHog Cloud, opt-in/manual events only, no replay or autocapture; or
2. **Reliability:** Sentry Electron only, with crash/error reporting first and product analytics deferred; or
3. **Privacy-first product learning:** Aptabase self-hosted/managed plus a separately approved crash service.

For the stated requirement—UX event analytics plus error/crash tracking with low account burden—option 1 is the best starting point, provided the Electron bundle/process and data-scrubbing spike passes.

## Many-projects addendum (PostHog Cloud)

PostHog Cloud is convenient for a small portfolio, but the current free plan is not a “many projects” plan: it allows **1 project** and one-year retention. The current pay-as-you-go plan allows **6 projects** and seven-year retention; both plans list unlimited team members. The same pricing page lists monthly free allocations of 1M analytics events and 100K exceptions, with usage-based rates after those allocations. ([official pricing](https://posthog.com/pricing))

The pricing page presents project count and retention as plan entitlements, but the reviewed official material does not clearly state whether usage, billing limits, or retention quotas are pooled across an organization or metered independently per project. Treat the six-project allowance as an account/plan-level ceiling, not six independent free quotas. Confirm the exact allocation behavior in the account UI or with PostHog before creating a portfolio-wide organization.

Each app should still get its own PostHog project and project token. That keeps dashboards, event schemas, feature flags, opt-out configuration, and data access boundaries separate. Do not put unrelated apps into one project merely to avoid the project limit; that makes event names, identities, retention, and deletion boundaries harder to reason about. A practical low-maintenance pattern is one PostHog organization for up to six Forge3D-family apps, with a written mapping of app → project → token; beyond six, either consolidate only genuinely related variants or budget for another organization/vendor.

**Conclusion:** PostHog remains a good low-maintenance choice for a handful of separate apps, not an unbounded project registry. For Monroe’s likely small portfolio, the paid six-project allowance is probably sufficient; the free tier is suitable only for one flagship app or a single pilot.
