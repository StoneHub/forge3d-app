UX + product audit · 2026-07-12

Make Forge3D feel like one confident tool.

Forge3D already has more product than its public story admits. The highest-value upgrade is to turn its capable Design and Assembly surfaces into one legible maker journey—then ship that truth cleanly before expanding toward Print Mode.

Recommended: Direction A Guided Maker Flow preserves the serious IDE, exposes Assembly at the right moment, and gives first-run users an obvious path from an idea to a measured, exportable part.
Planning artifact only. No product code, branch, release, or deployment was changed.

What is working well

native OpenSCADreal geometrymeasurementlocal-first

  • The split editor/viewport layout matches the job and communicates technical credibility.
  • Automatic dimensions and Final-versus-Quick rendering create practical maker value.
  • Assembly keeps edits non-destructive and makes STL work possible without forcing code changes.
  • The Start catalog, Params UI, and integrated diagnostics bridge novice and expert use.

Where users may hesitate

too many entry pointsmode discoveryrelease mismatch

  • Start, Workspace, Quick Start, Templates, Params, and examples compete without a single recommended path.
  • Assembly appears as a toolbar action, but its value and prerequisite (“Final render”) are not explained as a journey.
  • Dense chrome uses small controls and low-contrast secondary text that can punish new users and low-vision users.
  • Public docs and catalog data do not reliably describe the checked-in capability or actual releases.
02 · Choose a product posture

Three distinct upgrade directions

These are intentionally different bets. Each reuses Forge3D’s current architecture and avoids premature Print Mode expansion.

OPTION A

Guided Maker Flow

BEST PATH

Keep the professional IDE, but add an outcome-based welcome and a visible progression: Start → Design → Final Render → Assemble → Export.

Core changes

  • First-run “What are you making?” chooser
  • Contextual next-step rail above status bar
  • Assembly readiness card after Final render
  • One consolidated Start surface
  • Short, dismissible prerequisite checks

Best for

New makers who need direction, without slowing experienced OpenSCAD users.

Risk

Guidance can become noisy. It must disappear once the user demonstrates the workflow.

OPTION B

Builder-First Workbench

Position Forge3D as the missing Mac-native quick STL workbench. Launch into a project hub where “Inspect / combine an STL” is as prominent as “Write OpenSCAD.”

Core changes

  • Project hub with Design and Builder entry cards
  • Assembly as a first-class start mode
  • Inspector-first right rail
  • Recent STL and scene history
  • Measurement and boolean recipes

Best for

Users missing Microsoft 3D Builder for quick measure, merge, cut, orient, and export jobs.

Risk

The product may look like a mesh editor with an attached IDE, weakening its differentiated OpenSCAD identity.

OPTION C

Power-User Studio

Lean into Forge3D as a serious programmable modeling environment: command palette, layout presets, richer source navigation, history, and persistent project sessions.

  • Command palette and searchable actions
  • Modeling / Debug / Assembly layouts

Best recommendation: A

Why: Forge3D does not need another identity or another broad feature set yet. It needs a clear story across what is already there. Guided Maker Flow creates that story while retaining both the programmable IDE and the Builder promise.

Next step: prototype only the welcome chooser, stage strip, and post-render Assembly handoff against the current interface. Test whether a new user can explain the three stages after five minutes.

Counterpoint

If Monroe’s strongest personal pain is specifically “Microsoft 3D Builder on Mac,” Option B may be the emotionally sharper product and marketing hook. The risk is trying to win a broad STL-editor category before hardening the existing Builder path and release distribution.

Option C is valuable later, especially History and command palette, but it should follow—not precede—journey coherence.

04 · Phased plan

Wrap the product before widening it

This plan is deliberately gate-based. Each phase has a product truth check before the next layer begins.

Gate 0

Reconcile truth

Decide which branch is canonical, compare it with origin/main, and document which Assembly capabilities are actually release-ready. Update README, status, roadmap, catalog metadata, screenshots, and version claims together. Do not market unmerged or unvalidated work.

Phase 1

Prototype the chosen posture

Build a disposable interaction prototype for the selected direction. For Option A, limit it to three elements: first-run outcome chooser, persistent stage strip, and a contextual “ready for Assembly” handoff.

Phase 2

Simplify entry and chrome

Consolidate Start/Quick Start/template entry points, increase high-value control targets, improve contrast, and move secondary toggles into contextual menus. Preserve keyboard shortcuts and resizable panels.

Phase 3

Harden the full maker journey

Dogfood three tasks: create a parametric part, import and measure an STL, combine two parts and export. Capture failures at every transition—OpenSCAD missing, stale render, boolean failure, locked part, scene save failure.

Phase 4

Release the proof

Produce current Design and Assembly screenshots, a 45–60 second demo, accurate installer/prerequisite copy, and a release checklist. Confirm the downloaded artifact—not only a source build—matches the public claims.

Later

Only then choose expansion

Add the strongest slice from B (Builder-first launch) or C (History / command palette). Keep Print Mode separate until Assembly is legible, reliable, and genuinely used.

Accessibility

  • 44px targets for primary toolbar and mode controls
  • Visible focus and complete keyboard traversal
  • Do not encode state by cyan/amber color alone
  • Raise contrast for metadata, inactive tabs, and dimensions
  • Text alternatives for viewport state and measurement history

Performance

  • Keep booleans and native renders off the renderer thread
  • Expose progress and cancellation consistently
  • Avoid rebuilding Three.js scenes for unrelated UI state
  • Virtualize long Start/Workspace/part lists
  • Record task timings before promising “instant” workflows

Onboarding

  • Detect OpenSCAD before asking users to build
  • Offer a known-good example and explicit first task
  • Explain Quick vs Final at point of use
  • Teach Assembly via a two-part fit exercise
  • Let repeat users permanently dismiss coaching
